# Phase 04 — PostgreSQL database integrity and architecture audit

**Repository:** SuvdDent

**Branch:** `feature/suvd-dent-backend-completion`

**Audited commit:** `5f26ef0040458af57ba0a6f01426dfefdeb46b97`

**Scope:** Repository source, EF Core PostgreSQL model/migrations, services, and tests.

**Database access:** None. No PostgreSQL connection was opened and no SQL in the companion audit script was executed.

## Executive summary

At the audited commit, the PostgreSQL model used four ordered migrations and had substantial tenant-safe composite foreign keys. Appointment writes use serializable transactions and idempotency keys; appointment/outbox persistence has explicit checks and restrictive deletion. The test suite also has real-PostgreSQL concurrency tests, but these are opt-in and were not run for this audit.

This review found **no confirmed Critical or High severity defect**. It did find confirmed schema-level integrity gaps: `Users` and `Services` do not reference `Clinics`; appointments independently reference a doctor and service without requiring their doctor-service mapping; and several business invariants (price ranges and service-name uniqueness) are enforced only in API code. The absence of database exclusion constraints means non-application writers can also bypass appointment/availability overlap checks.

The user-provided environment inventory (two clinics, twelve users, etc.) is treated as **unverified input**, not as a finding from this audit. Actual migration history, constraints, indexes, sequence state, role grants, and row integrity must be checked later using [the read-only SQL audit](DATABASE_INTEGRITY_AUDIT_PHASE_04_READ_ONLY.sql).

**Follow-up status:** The tenant-root foreign-key gap recorded as F-01 below was addressed in the current worktree by additive SQLite and PostgreSQL migrations, including `20261125115303_AddPostgreSqlClinicTenantRootForeignKeys`. The companion SQL now expects the five-migration PostgreSQL chain. This follow-up did not connect to a database, so deployment state remains unverified here; the findings retain their meaning at the audited commit.

**Follow-up offline validation:** Release build succeeded with 0 warnings and 0 errors. The offline suite reported 504 total, 491 passed, 13 skipped, and 0 failed. PostgreSQL opt-in tests were skipped; no live database was contacted.

## 1. Architecture derived from the repository

- `AppDbContext` is the shared relational model; `PostgreSqlAppDbContext` isolates PostgreSQL migration discovery and uses a separate PostgreSQL model snapshot. PostgreSQL credentials are obtained from the environment, and production startup requires explicit approval. The PostgreSQL startup path checks applied migration history and does not apply migrations; the SQLite path has different startup behavior. ([AppDbContext.cs](DentalApi/Data/AppDbContext.cs#L36), [PostgreSqlAppDbContext.cs](DentalApi/Data/PostgreSqlAppDbContext.cs#L7), [DatabaseProviderSettings.cs](DentalApi/Services/DatabaseProviderSettings.cs#L24), [Program.cs](DentalApi/Program.cs#L235))
- The PostgreSQL migration chain is:
  1. `20261027132306_PostgreSqlBaseline`
  2. `20261027180725_AddPostgreSqlAppointmentFoundation`
  3. `20261102165221_AddPostgreSqlNotificationOutbox`
  4. `20261102180315_AddPostgreSqlPhoneVerificationChallenges`
  5. `20261125115303_AddPostgreSqlClinicTenantRootForeignKeys`
- Those migrations define 13 baseline tables, then `Appointments`, `NotificationOutbox` plus `NotificationPreference`, and `PhoneVerificationChallenge`: 17 application tables total, excluding `__EFMigrationsHistory`. The model uses integer `GENERATED BY DEFAULT AS IDENTITY` for integer `Id` keys, UUIDs for outbox/challenge IDs, text/string enum mappings, and provider-specific timestamp representations. ([PostgreSqlBaseline.cs](DentalApi/Migrations/PostgreSql/20261027132306_PostgreSqlBaseline.cs#L18), [PostgreSql appointment migration](DentalApi/Migrations/PostgreSql/20261027180725_AddPostgreSqlAppointmentFoundation.cs#L15), [PostgreSql notification migration](DentalApi/Migrations/PostgreSql/20261102165221_AddPostgreSqlNotificationOutbox.cs#L14), [PostgreSql challenge migration](DentalApi/Migrations/PostgreSql/20261102180315_AddPostgreSqlPhoneVerificationChallenges.cs#L14))
- PostgreSQL migrations are not generated or applied by API startup. Startup compares the entire applied migration-ID sequence against the application’s expected sequence. This is not a live structural comparison of columns, indexes, or constraints. ([DatabaseProviderSettings.cs](DentalApi/Services/DatabaseProviderSettings.cs#L72), [Program.cs](DentalApi/Program.cs#L241))
- The model has no global EF query filters or PostgreSQL row-level security configuration. Tenant scoping is primarily implemented in services/controllers and reinforced by composite foreign keys where configured.

## 2. Relationship inventory

| Table | Keys and relationships in the source model |
|---|---|
| `Clinics` | PK `Id`. Optional timezone verifier FK `(TimeZoneVerifiedClinicId, TimeZoneVerifiedByUserId)` → `Users(ClinicId, Id)`. A check requires the verifier fields to be consistently null while pending, or populated with an allowed verified timezone/location. |
| `Users` | PK `Id`; alternate unique key `(ClinicId, Id)` supports dependent tenant FKs. Unique filtered `(ClinicId, Email)` and `(ClinicId, Phone)`. **No FK from `ClinicId` to `Clinics`.** |
| `Services` | PK `Id`; alternate unique key `(ClinicId, Id)` supports dependent FKs. **No FK from `ClinicId` to `Clinics`.** No database uniqueness for service name. |
| `Patients` | PK `Id`; alternate unique `(ClinicId, Id)`. Optional composite FK `(ClinicId, UserId)` → `Users(ClinicId, Id)`, allowing an unlinked, clinic-managed patient. Filtered unique `(ClinicId, UserId)` when `UserId` is non-null. |
| `DoctorProfiles` | PK `Id`; alternate unique `(ClinicId, Id)`. Restricted FK to `Clinics`; composite FK `(ClinicId, UserId)` → `Users(ClinicId, Id)`; unique `(ClinicId, UserId)`. No FK/check enforces that the linked user’s role is `Doctor`. |
| `DoctorWorkingHours` | PK `Id`; composite FK `(ClinicId, DoctorProfileId)` → `DoctorProfiles(ClinicId, Id)`. Unique `(ClinicId, DoctorProfileId, DayOfWeek, StartMinute)` and a weekday/minute interval check. |
| `DoctorServices` | PK `Id`; composite FKs to doctor profile and service using `(ClinicId, DoctorProfileId)` and `(ClinicId, ServiceId)`. Unique `(ClinicId, DoctorProfileId, ServiceId)`, plus a service-leading index. Duration and buffer bounds are checked. |
| `PatientAvailabilitySchedules` | Composite PK `(ClinicId, PatientId)` and composite FK to `Patients(ClinicId, Id)`. Version is a concurrency token. |
| `PatientAvailabilities` | PK `Id`; composite FK `(ClinicId, PatientId)` → schedule. Unique `(ClinicId, PatientId, StartUtc)` and a positive, bounded tick interval check. |
| `Appointments` | PK `Id`, plus alternate unique `(ClinicId, Id)` for outbox references. Restricted FK to clinic and composite FKs to patient, doctor profile, and service. Unique idempotency key `(ClinicId, PatientId, RequestId)`. No FK to the matching `DoctorServices` row and no exclusion constraint preventing overlaps. |
| `VerificationCodes` | PK `Id`; FK `UserId` → `Users(Id)` with `ON DELETE CASCADE`; index on `UserId`. No database domain checks for channel, expiry, or failed-attempt range. |
| `PlatformAccounts` | Global PK `Id`; nullable email/phone with a check requiring at least one contact and unique filtered email/phone indexes. PostgreSQL email uses the `platform_email_nocase` ICU collation. |
| `PlatformVerificationCodes` | PK `Id`; restricted FK to global platform account; composite lookup index `(PlatformAccountId, Channel, Purpose, CreatedAt)`. No database checks for channel/purpose/expiry/attempt range. |
| `ClinicPatientLinks` | PK `Id`; restricted FK to platform account and composite FK `(ClinicId, PatientId)` → `Patients(ClinicId, Id)`. Unique `(ClinicId, PatientId)` and `(PlatformAccountId, ClinicId)`. The account is global; the patient side is clinic-bound. |
| `NotificationPreference` | Composite PK `(ClinicId, UserId)` and restricted composite FK to `Users(ClinicId, Id)`. |
| `NotificationOutbox` | UUID PK; restricted composite FK `(ClinicId, AppointmentId)` → `Appointments(ClinicId, Id)`; unique `(ClinicId, AppointmentId, Event, Channel)`. |
| `PhoneVerificationChallenge` | UUID PK; restricted clinic FK and composite user FK `(ClinicId, UserId)` → `Users(ClinicId, Id)`. Partial unique index allows one unconsumed/uninvalidated challenge per user/clinic. |

Most core dependent relationships use composite tenant keys, preventing a patient, doctor, or service from another clinic from being attached when the relevant foreign keys exist. The table inventory and orphan checks in the companion SQL are intended to confirm the deployed catalog and data, not to assume it matches EF metadata.

## 3. Existing constraints, nullability, and index coverage

### Keys, uniqueness, and checks

- Every entity table has a primary key; `PatientAvailabilitySchedules` uses a composite key. Parent alternate keys support tenant-aware FKs.
- Unique constraints/indexes cover tenant-scoped user email/phone, patient-to-user, doctor-to-user, doctor-service mappings, working-hour start keys, availability start keys, appointment idempotency, and outbox event/channel idempotency. Platform account contact uniqueness is global.
- Database checks cover verified clinic location/timezone state; doctor service duration and buffers; working-hour weekday/minute ranges; patient availability intervals; appointment status, non-empty request ID, finite timestamps, timezone snapshot, occupied/treatment interval ordering and snapshot arithmetic; platform-account contact presence; notification event/channel/state/attempts and reminder channel; and challenge expiry/attempts/delivery/consumed state.
- Service prices have PostgreSQL `bigint` storage (whole MNT units in the current API), but no database range/order check. `User.Role`, verification-code domain strings, and several user-facing fields also lack database enum/range checks.
- Required EF properties are generated as `NOT NULL` in migrations. Intentional optional fields include `User.Email`/`Phone`, `Patient.UserId`, patient birth date and free-text medical/address fields, `Service.MaxPrice`, platform email/phone individually, and nullable verification metadata. `Patient.UserId` being nullable is a supported case, not an orphan defect.

### Indexes

The model/migrations include PK/alternate-key indexes; tenant-scoped user contact indexes; patient `(ClinicId,UserId)` plus `UserId`; doctor `(ClinicId,UserId)`; doctor-service unique mapping and `(ClinicId,ServiceId)`; working-hour and patient-availability unique interval-start indexes; platform email/phone unique indexes; verification-code lookup indexes; appointment `(ClinicId,PatientId,RequestId)`, `(ClinicId,PatientId,StartUtc)`, doctor/status/occupied-time, and service indexes; outbox event idempotency and `(State,NextAttemptUtcTicks)`; and phone-challenge active uniqueness and lookup indexes.

`Patients.UserId` is a **candidate redundant index**, not a confirmed waste: current tenant-scoped queries generally also constrain `ClinicId`, which the composite unique index can serve. Confirm with production `pg_stat_user_indexes` deltas and `EXPLAIN (ANALYZE, BUFFERS)` before considering removal. Index scan counts reset and a low count alone is not proof of redundancy. Other indexes have different leading columns or serve FK/queue access patterns; no additional index is recommended for removal from source review alone.

## 4. Findings and severity

Severity describes the database-integrity risk. A confirmed schema gap does not mean the reported live rows currently violate it.

### Confirmed schema gaps

| ID / severity | Finding and evidence | Impact and classification |
|---|---|---|
| **F-01 — Medium (addressed in follow-up source)** | At the audited commit, `Users.ClinicId`, `Services.ClinicId`, and `Patients.ClinicId` lacked restrictive FKs to `Clinics.Id`. The current worktree adds those relationships in the shared model and additive provider migrations; see `20261125115303_AddPostgreSqlClinicTenantRootForeignKeys`. ([AppDbContext.cs](DentalApi/Data/AppDbContext.cs#L87), [PostgreSQL tenant-root migration](DentalApi/Migrations/PostgreSql/20261125115303_AddPostgreSqlClinicTenantRootForeignKeys.cs)) | The audited source allowed orphan tenant roots through direct writes. Current source closes that gap without changing nullable `Patients.UserId`; migration/deployment status and live orphan data were not verified in this follow-up. |
| **F-02 — Medium** | An appointment has separate same-clinic FKs to its doctor and service, but no composite FK to `DoctorServices(ClinicId, DoctorProfileId, ServiceId)`. The mapping table already has a unique key suitable as a principal key. `AppointmentService.Configuration` checks an active mapping before normal booking. ([AppointmentModelConfiguration.cs](DentalApi/Data/AppointmentModelConfiguration.cs#L11), [AppDbContext.cs](DentalApi/Data/AppDbContext.cs#L112), [AppointmentService.cs](DentalApi/Services/AppointmentService.cs#L82)) | Direct SQL or a future writer can combine an existing same-clinic doctor and service that are not mapped. Existing API booking is guarded; persisted-data defect is unverified. |
| **F-03 — Medium** | PostgreSQL has no exclusion constraint for overlapping confirmed appointments or patient availability ranges. The appointment index is a lookup index, not an overlap constraint; a persistence test explicitly demonstrates direct inserts of overlapping appointments. Normal writes use PostgreSQL `SERIALIZABLE` and test concurrency behavior. ([AppointmentModelConfiguration.cs](DentalApi/Data/AppointmentModelConfiguration.cs#L25), [DatabaseCompatibility.cs](DentalApi/Services/DatabaseCompatibility.cs#L13), [AppointmentPersistenceTests.cs](DentalApi.IntegrationTests/AppointmentPersistenceTests.cs#L264), [PostgreSqlAppointmentTests.cs](DentalApi.IntegrationTests/PostgreSqlAppointmentTests.cs#L61)) | Application writes are protected by service logic/serialization, but non-application writers can violate the invariant. This is a confirmed database guarantee gap, not evidence that concurrent API booking currently fails. |
| **F-04 — Medium** | `Services.MinPrice` and `MaxPrice` have no database check. API DTO validation constrains each to `0..1,000,000,000` and checks `MaxPrice >= MinPrice`. ([Entities.cs](DentalApi/Models/Entities.cs#L56), [AdminServicesController.cs](DentalApi/Controllers/AdminServicesController.cs#L22), [PostgreSqlBaseline.cs](DentalApi/Migrations/PostgreSql/20261027132306_PostgreSqlBaseline.cs#L41)) | Raw writes/imports can store negative or reversed ranges; estimates consume these stored values. API validation does not protect bulk loads or future writers. No current invalid price rows were inspected. |
| **F-05 — Medium** | Service name uniqueness is a check-then-write in `AdminServicesController`; no unique index/constraint exists on normalized name and clinic. Create/update do not wrap the duplicate check and write in a serializable transaction. ([AdminServicesController.cs](DentalApi/Controllers/AdminServicesController.cs#L71), [AdminServicesController.cs](DentalApi/Controllers/AdminServicesController.cs#L99), [PostgreSqlBaseline.cs](DentalApi/Migrations/PostgreSql/20261027132306_PostgreSqlBaseline.cs#L41)) | Concurrent director requests can pass the same precheck and persist case-insensitive duplicate catalog names. This is a confirmed race window. Existing duplicate rows are unknown. |
| **F-06 — Low** | User email uniqueness is a normal case-sensitive PostgreSQL unique index; registration lowercases email and login lowercases the input. The special ICU case-insensitive collation is configured for `PlatformAccount.Email`, not `User.Email`. ([AppDbContext.cs](DentalApi/Data/AppDbContext.cs#L48), [AppDbContext.cs](DentalApi/Data/AppDbContext.cs#L160), [AuthController.cs](DentalApi/Controllers/AuthController.cs#L77), [AuthController.cs](DentalApi/Controllers/AuthController.cs#L612)) | API-created values are normalized, but raw imports can create case variants that the unique index regards as distinct; an uppercase-only user email will not match the lowercased login lookup. Existing rows were not checked. |
| **F-07 — Low** | Some state domains are enforced only by application code. `User.Role` is stored as text without a check; `VerificationCodes` and `PlatformVerificationCodes` have no channel/purpose/expiry/attempt checks; outbox checks do not require `SentUtcTicks` exactly when `State='Sent'` or constrain tick signs. Appointment status is constrained to known values, but there is no database transition/history rule. ([AppDbContext.cs](DentalApi/Data/AppDbContext.cs#L58), [NotificationModelConfiguration.cs](DentalApi/Data/NotificationModelConfiguration.cs#L25), [VerificationCode.cs](DentalApi/Models/VerificationCode.cs#L4), [PlatformAccount.cs](DentalApi/Models/PlatformAccount.cs#L17), [AppointmentModelConfiguration.cs](DentalApi/Data/AppointmentModelConfiguration.cs#L58)) | Direct writes can create state that normal services do not produce. The intended lifecycle for any additional database checks should be confirmed before adding them; no invalid rows are confirmed. |

## 5. Existing regression coverage and gaps

### Coverage found

- `TenantIntegrityTests` applies real SQLite migrations and verifies same-clinic composite user links, rejects cross-clinic/missing user references, preserves existing data, and exercises restrictive deletes.
- `AppointmentPersistenceTests` checks migration additivity, same-clinic FKs, interval/snapshot/status/request checks, UTC round trips, request-key uniqueness, and intentionally confirms that the lookup indexes do **not** prevent all overlaps.
- `AppointmentMigrationMetadataTests` and `PostgreSqlBaselineTests` generate PostgreSQL SQL offline, verify PostgreSQL identity/timestamp/collation mappings, and assert no pending EF model changes.
- `PostgreSqlAppointmentTests` uses independent PostgreSQL backends at `SERIALIZABLE` and races overlapping bookings and duplicate requests. It is an opt-in real-PostgreSQL test.
- `NotificationMigrationTests`, `PlatformMigrationTests`, `PhoneVerificationMigrationTests`, and scheduling migration tests cover metadata, additive migration behavior, constraints, and model snapshots, primarily with SQLite.
- `AppointmentApiTests` covers owner/clinic isolation, cancellation idempotency, and transactional outbox enqueue/processing behavior.

### Missing or incomplete scenarios

1. Direct inserts of a user/service referencing a nonexistent clinic; direct appointment insert with no matching doctor-service mapping.
2. PostgreSQL exclusion/constraint tests for overlaps from direct SQL and for concurrent patient-availability overlap writers.
3. Concurrent same-clinic service-name create/update calls and database enforcement of normalized uniqueness.
4. Raw SQL negative/oversized/reversed service-price tests; invalid role/domain-state tests for users and verification tables; outbox `SentUtcTicks`/state consistency tests.
5. Mixed-case user-email uniqueness/login compatibility tests on PostgreSQL.
6. PostgreSQL migration application/catalog assertions against an isolated disposable PG instance; current provider metadata tests do not connect to PG.
7. Identity sequence drift after explicit-ID imports.
8. Deployment-role checks for ownership, superuser/DDL/truncate privileges, default privileges, and RLS. These are operational, not EF unit-test concerns.

At the original audit time, the 491-test baseline and 12 PostgreSQL skips were supplied by the user. No test suite was run as part of that source-only audit.

## 6. Prioritized remediation plan and migration proposals

Except for the tenant-root FK change noted below, these are proposals, **not implemented**. Do not edit historical migrations. First inspect the target with the read-only SQL and review every returned row with the data owner; do not auto-delete or rewrite data.

1. **Tenant roots — implemented in current source:** Additive provider migrations now add `ON DELETE RESTRICT` FKs from `Users.ClinicId`, `Services.ClinicId`, and `Patients.ClinicId` to `Clinics.Id`. The migration does not repair data; the companion read-only SQL reports any missing clinic references. Confirm the target database migration history and constraints during a separately authorized verification.
2. **Appointment mapping:** Add a composite FK from `Appointments(ClinicId, DoctorProfileId, ServiceId)` to the existing unique `DoctorServices(ClinicId, DoctorProfileId, ServiceId)` key. Existing appointment mappings must be reviewed first. Since service mapping rows are deactivated rather than deleted, a regular FK should preserve historical appointments while the API continues to require `IsActive` at booking time.
3. **Money and catalog uniqueness:** Add a `Services` check enforcing `MinPrice` within the API-supported whole-MNT range and `MaxPrice` null or between `MinPrice` and the same maximum. Add a unique expression index for `(ClinicId, lower(btrim(Name)))` to close the create/update race. Resolve existing duplicates by a separately approved data decision before creating the index.
4. **Overlap invariants:** If all writers cannot be guaranteed to use the current serializable application service, add database exclusion constraints for confirmed appointment doctor occupied ranges and patient treatment ranges, plus patient-availability ranges. PostgreSQL equality-plus-range exclusion typically requires `btree_gist`; confirm extension policy and deployment privileges first. Keep serializable transactions as defense in depth. If the application service is the explicitly enforced sole writer, retain the current design but document that trust boundary.
5. **State checks:** Add a database check for `Users.Role` using the current enum values. Consider checks for `VerificationCodes`, `PlatformVerificationCodes`, and outbox timestamp/state consistency only after confirming all legacy rows and lifecycle semantics. Avoid a trigger solely to record appointment status transitions unless audit history requirements call for it.
6. **Email normalization:** Audit case-folded duplicates and either enforce a normalized storage contract or add a PostgreSQL functional unique index on clinic plus normalized email. Coordinate with registration, login, and any import path.
7. **Least privilege:** Provision a dedicated non-owner API role with only required `CONNECT`, schema `USAGE`, table DML, and sequence `USAGE` privileges. Use a separate migration/owner role; do not grant runtime `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, ownership, `SUPERUSER`, `CREATEDB`, or `CREATEROLE` without a documented exception. Consider RLS only as a separately designed defense-in-depth change with transaction-local tenant context and connection-pool tests.
8. **Operational verification:** Run the companion SQL under a read-only role against the approved target after authorization. Compare catalog outputs to the PostgreSQL model snapshot and migration history. Investigate sequence state and index usage separately; do not infer defects from sequence gaps or reset statistics.
